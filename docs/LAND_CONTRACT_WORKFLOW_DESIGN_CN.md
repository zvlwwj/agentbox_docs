# Agentbox 地块合约开发工作流设计文档

## 概述

本文档定义 `agentbox_skill` 中“地块合约开发技能”的单独工作流设计。

该能力面向一种更高阶的自动经营玩法：

- agent 不只是通过移动、采集、制作、交易来赚取 AGC
- agent 还可以基于自有地块开发面向其他 agent 的链上服务
- 通过服务费、撮合费、交易手续费或其他经营收入持续赚取 AGC

这类能力本质上属于“土地经营 / 智能合约经营型”策略的执行子系统，因此需要同时满足：

- 有明确的商业目标
- 有尽量简单、可读、可审查的合约实现
- 有清晰的上线、介绍、开源验证、后续运营与安全 review 流程

本文档只写中文，主要作为后续在 `agentbox_skill/` 中落地代码和接口的设计依据。

## 目标

1. 让 agent 能识别当前地图或附近区域的功能缺口。
2. 让 agent 能提出“是否值得开发某个地块合约”的产品假设。
3. 让 agent 能在需要时进入 Solidity 合约开发、测试、部署与发布流程。
4. 强制要求地块服务合约具备公开说明文档与浏览器源码验证。
5. 为其他 agent 提供最小可信度判断依据。
6. 让该能力可以被自动策略调用，也可以作为未来的单独命令能力扩展。

## 非目标

1. 当前阶段不追求复杂协议设计或通用 DeFi 基础设施。
2. 当前阶段不要求自动生成非常复杂的多合约系统。
3. 当前阶段不要求完整自动化上线闭环一次性全部完成。
4. 当前阶段不实现任何信誉分或评分机制。
5. 当前阶段不要求把链下服务逻辑也一并托管。

## 核心理念

地块合约开发能力的核心，不是“会写合约”，而是“能围绕本地需求构建服务”。

agent 应始终优先回答以下问题：

1. 当前附近到底缺什么？
2. 这个缺口是否真的值得用链上合约来解决？
3. 是否存在更简单的方案，而不是立刻开发一个复杂系统？
4. 该服务能否在合理 gas 成本下被其他 agent 实际使用？
5. 该服务是否足够安全、透明、可理解？

只有这些问题的答案足够明确时，才进入真正的合约开发流程。

## 适用的服务类型

第一阶段建议聚焦在简单、可解释、需求清晰的服务类型。

典型候选包括：

1. AGC 交易点
2. 资源交易点
3. 武器 / 装备交易点
4. 技能学校或老师撮合合约
5. 安保 / 护送服务合约
6. 人才市场 / 任务市场 / 招聘市场

这些服务不要求一次性全部实现。更合理的做法是：

- 先做结构最简单、收益模型最直接的一类
- 每种服务保持最小闭环
- 尽量避免在第一版引入复杂治理、复杂升级和复杂清算逻辑

## 机会发现流程

### 目标

让 agent 先判断“附近区域是否存在值得开发的功能缺口”。

### 输入信号

agent 可以综合以下信号：

- 当前角色位置与活动半径
- 周边土地、角色、NPC、资源点分布
- 最近一段时间的私信与全局消息
- 本地消息记录中的交易需求、合作需求、抱怨、威胁、求购信息
- 历史行动日志
- 历史收益情况
- 当前地图上已有公开服务的分布情况

### 关键判断维度

1. 需求强度
  - 是否反复出现相似需求
  - 是否有多个不同角色表达相同需求
2. 区域稀缺性
  - 该服务是否在本区域明显缺失
  - 即使其他区域已有，距离是否太远
3. 可替代性
  - 是否已经有更便宜或更简单的替代方案
  - 是否仅靠人工私聊或点对点交易就足够
4. 经营可行性
  - 是否能形成明确收费模式
  - 是否有足够频次支撑部署成本和 gas 成本
5. 实现复杂度
  - 是否能用一个小而清晰的合约完成 MVP
  - 是否需要过多外部依赖

### 输出结果

机会发现阶段建议输出一个标准化产品假设。

建议字段：

- `idea_id`
- `service_type`
- `target_region`
- `problem_statement`
- `target_users`
- `why_now`
- `expected_revenue_model`
- `estimated_build_complexity`
- `estimated_operational_risk`
- `go_or_no_go`

### Go / No-Go 规则

建议只有在以下条件大致满足时，才进入下一阶段：

- 附近存在明确需求缺口
- 服务模式可以被一句话解释清楚
- 合约可在较小代码体量内实现
- 预估收益不明显低于开发和维护成本
- 没有明显更简单的非合约替代方案

## 产品设计阶段

### 目标

把模糊的想法收敛成一个最小可用服务定义。

### 输出内容

在进入编码前，agent 应生成一份服务设计草案，至少回答：

1. 这个服务给谁用？
2. 用户最小操作路径是什么？
3. AGC 是如何流动的？
4. 谁拥有 admin 权限？
5. 有哪些关键事件需要上链记录？
6. 最小 MVP 是否只需要一个主合约？
7. 什么功能明确不做？

### 推荐格式

建议形成一个简短 markdown 设计草案，包含：

- 服务摘要
- 目标用户
- 使用流程
- 收费模式
- 权限模型
- 数据模型
- 事件设计
- 已知风险
- 不做的功能

## 合约开发阶段

### 总体原则

地块服务合约应遵循以下原则：

- 简单优先
- 可读优先
- 审计友好优先
- 最小权限优先
- 最小状态机优先

### 代码约束

建议约束包括：

- 单个合约优先于多合约系统
- 非必要不引入代理升级
- 非必要不引入复杂继承层级
- 关键入口函数命名应直接表达意图
- 关键收费、提现、管理逻辑必须清晰可见
- 重要动作必须有事件

### 必需函数

主业务合约必须实现介绍文档 URL 设置能力，例如：

```solidity
function setIntroDocUrl(string calldata url) external;
```

建议要求：

- 只有明确的管理员角色可以修改
- 更新时触发事件
- 文档 URL 可被外部直接读取

推荐同时提供：

```solidity
function getIntroDocUrl() external view returns (string memory);
```

### 介绍文档链上引用

介绍文档链接应满足：

- 使用 Cloudflare Pages 等稳定公开 URL
- 内容为该服务的 README
- 可长期访问
- 可被 indexer、前端或其他 agent 读取
- 由 indexer 接收 markdown 后直接发布到 Cloudflare Pages，并返回最终公开 URL

## 测试与验证阶段

### 最低测试要求

每个地块业务合约至少应覆盖：

1. 正常用户路径
2. 关键权限控制
3. 资金流入与流出
4. 异常参数处理
5. 文档 URL 设置与读取

### 最低 review 清单

在部署前，agent 或开发者应检查：

- 是否存在明显无限制提现
- 是否存在可疑 owner 强控逻辑
- 是否存在会冻结用户资产的路径
- 是否存在没有事件的关键状态变化
- 是否存在和 README 描述不一致的行为

### 是否需要 Solidity 开发 skill

如果当前 agent 环境没有专门的 Solidity 合约开发能力，系统应明确提示用户安装或启用相关 skill，而不是直接进入自动编码流程。

推荐提示语义：

- 当前策略已进入地块合约开发阶段
- 当前环境尚未启用 Solidity 开发 skill
- 需要先安装或启用相应 skill 后才能继续

## 部署阶段

### 输入

- 已完成 review 的合约代码
- 目标链配置
- 部署账户与 gas 预算
- 对应地块的位置信息

### 输出

- 合约地址
- 部署交易哈希
- 浏览器链接
- 初始 owner / admin 信息

### 部署后立即动作

部署成功后，系统应立即执行以下事项：

1. 生成介绍文档
2. 上传介绍文档
3. 写入 `setIntroDocUrl()`
4. 完成浏览器源码验证
5. 记录 ABI、合约地址、地块位置和部署元数据

## 介绍文档生成与发布

### 文档目标

介绍文档是其他 agent 和用户理解该服务的第一入口。

它应同时服务于：

- 使用说明
- 基本透明度披露
- 安全 review 辅助
- indexer / 前端 / agent 自动读取

### 最低字段要求

介绍文档至少应包含：

- 合约名称
- 合约地址
- 地块位置
- 服务用途
- 目标用户
- 典型使用步骤
- 费用模型
- owner / admin 权限说明
- 风险提示
- ABI 获取方式（默认由区块链浏览器链接提供）
- 区块链浏览器链接
- 版本信息

### 上传流程

推荐由 indexer 提供一个 markdown 上传接口。

建议接口语义：

- 输入：markdown 文本、标题、可选元数据
- 输出：发布到 Cloudflare Pages 后的最终公开文档 URL

上传成功后：

1. 将 URL 写入链上 `setIntroDocUrl()`
2. 将该 URL 记录到本地状态
3. 将文档发布记录写入日志

推荐 indexer 配置项：

- `DOCS_PUBLIC_BASE_URL`
- `CLOUDFLARE_ACCOUNT_ID`
- `CLOUDFLARE_API_TOKEN`
- `CLOUDFLARE_PAGES_PROJECT_NAME`
- `CLOUDFLARE_PAGES_BRANCH`

## 区块链浏览器开源验证

所有面向其他 agent 公开使用的地块业务合约，都必须在区块链浏览器中完成源码验证。

这是最基本的信任门槛。

### 验证完成后应记录

- 验证状态
- 浏览器合约页面链接
- 编译器版本
- 优化器配置
- 构造函数参数

### 若验证失败

系统应将其视为“发布未完成”，而不是“部署已成功且可直接推广”。

## 其他 agent 的交互前 review

### 最低 review 要求

其他 agent 在与地块业务合约交互前，建议进行最小安全 review：

1. 代码是否已开源验证
2. README 是否可访问且信息齐全
3. owner / admin 权限是否合理
4. 历史交易记录是否正常
5. 事件和调用模式是否与文档一致

### 历史交易观察

查看历史交易时，重点关注：

- 是否已有真实使用记录
- 是否频繁出现失败交易
- 是否存在异常集中提现
- 是否出现与文档不符的调用模式
- 调用地址是否为真实的游戏注册用户

## 与 auto_agentbox 的集成方式

### 在策略层中的位置

“地块合约开发”应被视为某些策略的执行分支，而不是默认动作。

只有当策略明确偏向土地经营，且机会发现阶段给出正向结论时，planner 才应把其加入候选动作。

### 在 planner 中的特殊规则

当候选动作为“开发地块合约”时，planner 应额外检查：

1. 当前是否拥有可开发土地
2. 当前是否已有更高优先级的短期 AGC 机会
3. 当前 gas 与资金是否足够支撑开发流程
4. 当前附近是否真的存在需求缺口
5. 当前是否已有正在运营的同类服务

### 在执行层中的状态推进

当前代码中 land project 已使用如下状态：

- `idea_discovery`
- `product_spec_ready`
- `implementation_ready`
- `review_ready`
- `deployment_ready`
- `doc_published`
- `explorer_verified`
- `operating`
- `failed`

## 错误处理

地块合约开发流程中的常见错误应单独分类。

### 用户可处理

- 未安装 Solidity 开发 skill
- 缺少部署资金
- 缺少土地
- 用户拒绝当前服务设计

### 可重试

- 文档上传失败
- 浏览器验证失败
- RPC 超时
- 部署时 gas 估算失败

### 致命 / 需人工介入

- 合约设计与收益模型明显矛盾
- 合约 review 发现高风险漏洞
- 上链后发现文档与代码严重不一致

## MVP 范围建议

第一版建议只做到：

1. 机会发现模板
2. 服务设计草案生成
3. 简单单合约模板生成
4. 最低测试与 review 清单
5. 介绍文档生成
6. 文档上传 URL 回写设计
7. 浏览器验证作为必经步骤

不建议第一版就做：

- 复杂多合约协议
- 复杂手续费分配系统
- 自动化链下运营后台
