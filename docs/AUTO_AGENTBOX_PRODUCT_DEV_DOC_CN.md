# Agentbox 自动游玩代理产品/开发文档

## 概述

本文档定义了一个构建在现有 `agentbox_skill` player runtime 之上的新能力层：一个常驻可控的“自动游玩代理（auto player agent）”。它能够：

- 提供多套游戏攻略/策略
- 允许用户接受、拒绝或编辑策略
- 按照选定策略自动游玩游戏
- 每日汇总操作、资源变化、代币变化与 gas 使用情况
- 安全地暂停与恢复

目标是在不改变当前链上交互模型的前提下，把现有偏无状态的工具集升级为一个有状态、可恢复、可解释的自动化游戏助手。

本文档同时服务于两个目的：

- 作为面向产品设计的用户行为定义
- 作为面向实现的开发蓝图，指导在 `agentbox_skill/` 内落地

## 目标

1. 让用户通过一个简单命令启动 Agentbox 自动游玩。
2. 明确以“赚取 AGC 代币”为自动游玩代理的核心目标。
3. 在代理接管前，先向用户提供多套围绕 AGC 收益目标展开的策略供选择。
4. 支持用户不断切换策略，直到满意为止。
5. 使用现有 `agentbox_skill` 玩家工具执行游戏动作。
6. 持久化代理状态，使其可以在停止、重启或异常后恢复。
7. 自动生成每日行动报告。
8. 为用户提供明确的暂停、恢复、阅读策略、编辑策略等控制入口。

## 非目标

1. 当前阶段不需要支持多角色编队管理。
2. 当前阶段不需要支持多个自治代理之间的协作。
3. 当前阶段不需要管理员或 owner 类功能。
4. 当前阶段不要求实现收益最优策略。
5. 当前阶段不要求提供完整 Web UI。

## 用户命令

系统应支持以下高层命令。

### `start_agentbox`

预期行为：

1. 首先检查用户是否已经完成游戏注册并拥有角色。
2. 如果用户尚未注册，则优先进入注册流程，而不是直接进入策略确认或自动游玩。
3. 如果用户已注册但尚未有已批准策略，则进入策略确认流程。
4. 在首次策略确认阶段，用户不仅可以接受或拒绝候选策略，也可以直接通过和 agent 对话编辑当前策略。
5. 如果已有策略且代理处于暂停状态，则恢复自动执行。
6. 如果代理已经在运行，则返回当前状态，而不是启动重复循环。

预期返回：

- 当前运行状态
- 当前是否需要注册
- 当前策略版本
- 是否正在等待用户确认策略
- 是否已经开始或恢复自动游玩

### `stop_agentbox`

预期行为：

1. 将自动执行循环标记为暂停。
2. 停止规划新的动作。
3. 不尝试取消已经上链提交的交易。

预期返回：

- 状态已切换为 `paused`
- 最后一个已完成动作
- 当前是否仍存在待完成的异步链上动作

### `edit_strategy`

预期行为：

1. 读取当前策略。
2. 接收用户修改意见或编辑意图。
3. 产出一个新的候选策略版本。
4. 保留旧版本作为历史。
5. 新版本需要重新确认后才能生效。

预期返回：

- 新策略版本 id
- 变更摘要
- 状态 `pending_approval`

### `confirm_strategy`

预期行为：

1. 在用户意图无法从自然语言中明确判断时，作为显式确认命令使用。
2. 将当前候选策略或草稿策略确认成可生效版本。
3. 只有在确认后，系统才允许进入自动执行。

预期返回：

- 已确认的策略版本 id
- 当前 active strategy
- 状态 `approved`

### `read_strategy`

预期行为：

1. 返回当前激活中的策略。
2. 如果存在待确认草稿，则同时展示激活策略与草稿摘要。

预期返回：

- 当前激活策略内容
- 版本元信息
- 当前状态

## 主要用户路径

### 首次启动

1. 用户发送 `start_agentbox`
2. 系统首先检查用户是否已经完成角色注册
3. 如果尚未注册，则先进入托管注册流程
4. 用户完成注册
5. 注册完成后，系统再检查是否已有已批准策略
6. 如果没有，则代理生成多套候选策略
7. 用户查看策略 A
8. 用户此时有三种选择：
   - 直接接受该策略
   - 拒绝并切换到另一套策略
   - 通过对话方式要求 agent 修改当前策略
9. 如果用户要求修改，agent 生成当前策略的编辑版草稿并继续等待确认
10. 重复直到用户批准某一套原始策略或编辑后策略
11. 系统将该策略持久化为 active version
12. 代理启动自动游玩循环

### 后续恢复

1. 用户发送 `stop_agentbox`
2. 代理在安全边界暂停
3. 用户稍后再次发送 `start_agentbox`
4. 代理加载持久化状态和当前策略
5. 继续自动游玩循环

### 策略更新

1. 用户发送 `edit_strategy`
2. 代理读取当前策略和修改要求
3. 代理生成一个新的草稿版本
4. 用户确认草稿
5. 草稿变为新 active strategy
6. 后续自动决策使用新版本

## 产品需求

### 核心目标定义

自动游玩代理的核心目标应被定义为：

- 在可接受风险和 gas 成本范围内，尽可能持续赚取 AGC 代币

这里的“赚取 AGC”包括但不限于以下路径：

1. 通过资源采集后交易换取 AGC
2. 通过制作装备后交易换取 AGC
3. 通过购买土地并在土地上开发智能合约来赚取 AGC
4. 直接在地图上拾取 AGC

不同策略之间的主要差异体现在：

- 优先采用哪条 AGC 获取路径
- 风险控制强度
- 是否偏好主动经营类玩法，例如土地开发或合约经营
- 是否偏好短期快收益还是中长期积累
- 是否更强调稳定性还是更强调收益效率

### 策略提案

策略提案流程应满足：

- 以 LLM 驱动为主生成 2-3 套风格明显不同的策略
- 模板可以作为参考和约束，但不应成为主要生成方式
- 用自然语言解释各自取舍
- 允许用户拒绝并切换到下一套
- 允许用户在当前策略基础上编辑，而不是只能整套替换
- 首次策略选择阶段就支持通过对话直接编辑当前候选策略

策略风格示例：

1. 资源采集并交易型
2. 装备制作并交易型
3. 土地开发 / 智能合约经营型
4. 直接拾取 AGC 型
5. 低风险混合收益型

每套策略都应包括：

- 核心目标
- AGC 获取路径
- 风险偏好
- 移动策略
- 交互策略
- 战斗规避策略
- 代币安全策略
- 学习 / 制作优先级
- gas 消耗策略
- 停止条件

每套候选策略都必须明确回答：

1. 这套策略主要依靠什么方式赚取 AGC？
2. 这套策略的主要风险是什么？
3. 这套策略适合短期收益还是长期积累？
4. 这套策略在 gas 成本上是否划算？

### 地块合约开发技能

对于“土地开发 / 智能合约经营型”策略，系统应额外支持一类更高阶的 agent 能力：发现本地市场缺口，并在自有土地上开发可供其他 agent 使用的合约服务。

该能力的核心目标不是“为了部署而部署”，而是：

- 发现当前地图或附近区域中缺失、稀缺或交互成本过高的功能
- 用尽量简单、可读、可验证的合约把该功能产品化
- 通过交易、服务费、撮合费或经营收入来赚取 AGC

agent 在决定是否开发地块合约前，应先进行机会发现与需求分析。可重点观察：

- 当前地图上是否缺少 AGC 代币交易点
- 当前地图上是否缺少资源 / 武器 / 装备交易点
- 当前地图上是否缺少技能学校或教师撮合点
- 当前地图上是否缺少安保 / 护送 / 风险管理服务
- 当前地图上是否缺少人才市场、任务市场、招聘市场
- 即使全图已有类似服务，当前角色附近区域是否仍然存在明显供给不足

这里必须考虑游戏中的物理距离限制。即使远处已有类似设施，如果其他 agent 不愿意长距离移动，本地部署的服务仍然可能有明确价值。

地块合约开发工作流建议包括：

1. 发现需求并形成产品假设
2. 产出简洁可读的 Solidity 合约设计
3. 编写最小可用实现
4. 进行基本测试与审查
5. 部署到目标链
6. 设置介绍文档链接
7. 完成区块链浏览器源码开源验证
8. 将合约纳入后续运营、监控和收益分析

如果当前 agent 运行环境中还没有专门的 Solidity 开发能力，系统应在进入该工作流前明确提示用户安装或启用相应的合约开发 skill，而不是静默生成未经验证的合约代码。

合约实现要求：

- 合约代码应尽量简单、短小、可读
- 优先使用直接、易审计的状态机与权限模型
- 避免引入不必要的复杂代理、元编程或过度抽象
- 必须提供清晰的用户入口函数与事件
- 必须尽量减少会让其他 agent 难以理解的隐式行为

主业务合约必须实现一个用于设置介绍文档链接的函数，例如：

- `setIntroDocUrl(string calldata url)`

该链接预期是一个 Cloudflare Pages 链接，内容为该地块服务对应的 README / 介绍文档。

当前 `indexer` 已提供 markdown 文档发布接口，可接收 markdown 文本并直接发布到 Cloudflare Pages，返回可公开访问的文档 URL，供部署后写入 `setIntroDocUrl()`。

介绍文档应至少包含：

- 合约名称
- 合约地址
- 所在地块位置
- 服务用途与目标用户
- 使用方法
- 管理员 / owner 权限说明
- 收费或收益模式
- 风险提示
- ABI 获取方式（默认由区块链浏览器链接提供）
- 区块链浏览器链接

所有面向其他 agent 公开使用的地块业务合约，都必须在区块链浏览器中开源验证，以便其他 agent 或用户能够查看源码、ABI 和部署信息。

在其他 agent 与该合约交互前，系统应鼓励进行最小安全 review，至少包括：

- 检查源码是否已开源验证
- 检查 owner / admin 是否拥有过强权限
- 检查是否存在明显可疑的提现、冻结、升级或转移逻辑
- 查看历史交易记录，判断是否已有真实用户交互
- 查看事件和调用模式是否与介绍文档一致

第一阶段不引入任何“合约信任分 / agent 信任分”机制。MVP 阶段更现实的做法是先提供基础 review 清单、浏览器开源验证和历史交易可见性。

### 自动执行

自动游玩代理必须：

- 在行动前读取当前角色状态
- 避免非法状态切换
- 异步动作可完成时及时执行 finish
- 避免高频无意义写操作
- gas 过低时自动停止
- 记录所有动作与结果
- 所有行动都应尽量服务于 AGC 收益目标，而不是进行无收益的随机探索
- 能根据收到的私信或全局消息做出策略内允许的反馈

自动游玩代理应尽量：

- 优先选择当前位置附近的机会
- 减少无意义移动
- 在携带不可靠 AGC 时降低暴露风险
- 在低风险策略下避免危险交互
- 在不同 AGC 获取路径之间做符合当前策略的取舍
- 将私信视为高优先级环境信号，将全局消息视为中低优先级环境信号

### 每日报告

系统应每天生成一份 markdown 报告，包含：

- 日期
- 当日所用策略版本
- 尝试动作数
- 成功动作数
- 失败动作数
- gas 使用情况
- AGC 余额变化
- 资源库存变化
- 装备变化（如果有）
- 重要遭遇事件
- 重要消息输入与相应反馈
- 角色状态变化
- 代理自己的观察与思考
- 对策略的改进建议

## 功能范围

### 现有能力复用

实现时应优先复用：

- `agentbox_runtime.player_logic.PlayerRuntime`
- 当前 `agentbox_skill` 中已暴露的读工具
- 现有写操作 helper 与 precheck 逻辑
- 已实现的托管注册流程

当前还可直接复用的 land-dev 基础能力包括：

- `auto_agentbox.land_dev_service.LandDevService`
- `auto_agentbox.models` 中的 land project 状态模型
- `auto_agentbox.planner` 中的 `land.idea_discovery` 候选动作
- 本地 `state_store` 与 `message_store`
- indexer 文档发布 client
- explorer 验证 client

当前读工具已经支持双读源模式：

- `chain`：直接从链上 RPC 读取
- `indexer`：从 indexer API 读取聚合视图
- `auto`：优先尝试 indexer，失败时自动回退到链上

自动代理默认应优先采用 `source=auto`，同时保留在关键路径上显式指定读源的能力。

自动游玩层不应重复实现一套独立的链上交互逻辑，除非确实有必要。

### 当前实现状态

截至当前代码版本，以下能力已经落地：

- `land-dev` 第一阶段骨架已实现
- land project 状态模型已实现
- 机会发现、Go/No-Go、产品草案、合约草案、review 报告、README 生成功能已实现
- indexer `POST /docs/publish-markdown` 已实现
- indexer 到 Cloudflare Pages 的真实文档发布链路已打通
- explorer 验证 client 已接入 skill 侧

截至当前代码版本，以下能力仍未完成：

- `land-dev` 尚未正式接入完整 `auto_agentbox` 控制平面
- 还没有完整的 `start/stop/scheduler/runtime state` 自动运行闭环
- 尚未完成“自动策略触发 -> 合约真实部署 -> `setIntroDocUrl()` 写回 -> 浏览器验证 -> 运营”整条端到端生产闭环

### 需要新增的能力层

应在当前 runtime 之上增加一层 orchestrator。

建议承担以下职责：

1. 命令路由
2. 策略管理
3. 自动调度
4. 行动规划
5. 执行循环
6. 事件 / 动作日志
7. 每日报告生成

### 第 2.5 层：数据访问层

职责：

- 为 agent 提供统一的数据读取入口
- 根据场景选择 `auto`、`chain` 或 `indexer`
- 在 indexer 不可用时进行自动回退

推荐规则：

- 聚合视图优先使用 `indexer`
- 强一致判断优先使用 `chain`
- 默认使用 `auto`

适合优先走 `indexer` 的读取：

- `read.me`
- `read.global_config`
- `read.core_contracts`
- `read.land`
- 消息查询，例如私信与全局广播

适合优先走 `chain` 的读取：

- `read.action.finishable`
- 写操作前的 precheck
- 任何要求 tip-of-chain 最新状态的判断

当前 indexer 已有 `/messages` 接口，可支持：

- 按 `to_wallet` 查询发给当前角色的钱包私信
- 按 `from_wallet` 查询某个角色发出的消息
- 查询全局消息并作为环境信号
- 按 block 范围或时间范围做增量轮询

读取消息后，建议同步写入本地消息记录，以形成 agent 的长期上下文记忆。

## 注册要求

注册流程应被视为 `start_agentbox` 命令的一部分。

系统在进入策略确认或自动游玩之前，必须确保用户已经拥有一个可正常游玩的角色。

建议的注册闸门如下：

1. 在执行 `start_agentbox` 时，先检查是否已有有效角色。
2. 如果没有，则返回“需要注册”的状态，并进入托管注册流程。
3. 注册流程本身包括：
   - 创建托管钱包
   - 角色资料选择
   - 充值提示
   - 注册确认
4. 只有在注册成功之后，才继续后续的策略确认与自动游玩流程。

也就是说，注册不是一个独立于 `start_agentbox` 的旁路 onboarding，而是该命令的第一阶段。

## 系统架构

### 第 1 层：命令接口层

职责：

- 接收外部命令
- 将命令路由到策略层或执行层

输入：

- `start_agentbox`
- `stop_agentbox`
- `edit_strategy`
- `read_strategy`
- 未来可扩展为 `status_agentbox`

输出：

- 面向用户的状态结果

### 第 2 层：策略管理层

职责：

- 生成策略候选
- 持久化 active strategy
- 持久化 draft strategy
- 管理版本历史
- 在需要时生成土地经营 / 合约服务方向的候选方案

输入：

- 当前角色状态
- 历史报告
- 用户编辑意见
- 游戏约束条件

输出：

- 策略文档
- 策略元信息

### 第 3 层：行动规划层

职责：

- 将高层策略转成下一步候选动作
- 在土地经营策略下决定何时进行需求发现、何时进入合约开发工作流、何时优先运营已有合约

输入：

- 当前策略
- 当前链上状态
- 最近动作执行结果
- 本地消息记录与附近市场信号

输出：

- 下一步动作
- 选择该动作的理由
- 可选回退动作

### 第 4 层：执行层

职责：

- 安全调用 `PlayerRuntime`
- 归一化动作结果
- 记录遥测与日志
- 在土地开发场景下串联合约设计、测试、部署、验证、文档发布等步骤

### 第 5 层：调度层

职责：

- 控制 planner 执行时机
- 避免重复循环
- 响应暂停 / 恢复
- 触发日报

## Planner 规则

planner 应遵循如下决策顺序。

### 高优先级

1. 如果处于暂停状态，则不做任何动作。
2. 如果存在可完成的异步动作，则优先 finish。
3. 如果 gas 低于阈值，则停止并提示。
4. 如果角色状态异常或身份缺失，则停止并提示。

### 中优先级

1. 如果在保守策略下身上有高风险资产，则切换为避险行为。
2. 如果策略要求获取附近 AGC 机会，则优先评估当前位置附近可达目标。
3. 如果策略要求通过采集/制作/交易赚取 AGC，则先确认前置条件满足。
4. 如果策略要求通过土地开发赚取 AGC，则优先检查土地、合约部署条件和潜在回报。
5. 如果收到与交易、合作、威胁、求购、任务相关的消息，则将其作为决策输入并评估是否需要回应。
6. 如果准备开发地块合约，则先确认附近是否确实存在需求缺口，再决定是否投入开发成本。

### 低优先级

1. 探索
2. 可选社交动作
3. 机会型重新站位

### 消息响应规则

建议将消息分为两类：

1. 私信
2. 全局消息

私信处理建议：

- 优先级高于普通全局消息
- 如果与交易、合作、教学、威胁、求助有关，应进入 planner 的可响应事件队列
- 是否回复由当前策略决定
- 回复前应检查当前角色状态、位置风险和 gas 状态

全局消息处理建议：

- 作为环境信号而非强制命令
- 可用于识别附近风险、交易机会、资源热点或 AGC 机会
- 不必对每条全局消息都直接回复

允许的反馈形式包括：

- 发送私信回复
- 发送全局广播回应
- 修改移动路线
- 暂停低优先级行为
- 调整风险判断

## 执行循环

建议执行流程：

1. 读取状态。
2. 如果不是 `running`，则退出。
3. 确认注册已经完成。
4. 按需选择合适读源。
5. 使用 `read.me(source=auto)` 等聚合读获取角色状态。
6. 使用 `read.action.finishable(source=chain)` 获取当前动作是否可完成。
7. 使用 indexer 消息读取接口检查最近收到的私信和全局消息。
8. 将新消息写入本地消息记录，并更新消息处理状态。
9. 请求 planner 结合角色状态和消息上下文产出下一步动作。
10. 通过 `PlayerRuntime` 执行动作。
11. 记录结果。
12. 更新状态。
13. 根据动作类型 sleep 或 backoff。

读源选择建议：

- 角色总览、配置、土地等信息默认使用 `source=auto`
- finishable 判断固定优先使用 `source=chain`
- 如果某个读取当前没有 indexer 实现，则继续走链上
- 如果策略或 planner 明确要求最新状态，则强制使用 `chain`

建议时序：

- finishable 检查快循环：15-60 秒
- idle 决策慢循环：1-5 分钟
- 每日报告：按本地时间每天两次，分别在上午 10 点和晚上 10 点触发

## 调度模型

有两种比较实际的实现路线。

### 方案 A：进程内后台循环

优点：

- 实现简单
- 基础设施成本低

缺点：

- 进程退出后循环会停止
- 常驻可靠性较弱

### 方案 B：外部 Worker / Cron / Supervisor

优点：

- 可靠性更高
- 更适合做每日报告与长周期运行

缺点：

- 运维复杂度更高

推荐路线：

1. 正式实现直接采用外部 worker / cron / supervisor 模式。
2. 所有状态都必须落盘，确保 worker 可恢复。
3. `start_agentbox` 与 `stop_agentbox` 负责控制 worker 驱动的自动执行状态，而不是仅控制进程内循环。

## 安全约束

自动游玩层应对以下情况强制停止：

1. 钱包 ETH 余额低于 `0.001`
2. 连续交易失败
3. 角色身份不一致
4. chain id 不符合预期
5. 尚未确认策略却尝试执行

对于数据读取，还应增加以下安全规则：

1. 当使用 `source=auto` 时，indexer 不可用不应导致整个代理停止，应自动回退到链上读取
2. 当明确指定 `source=indexer` 时，如果 indexer 不可用，应显式报错
3. 关键写入前校验不应仅依赖 indexer 数据

建议增加的限制：

1. 每小时最大写操作数
2. 每日最大 gas 预算
3. 最大连续失败次数
4. 相似动作的最小间隔

## 命令语义

### `start_agentbox`

如果尚未注册角色：

- 进入 `awaiting_registration`
- 启动托管注册流程
- 优先完成注册
- 注册成功后再进入策略确认

如果注册完成后仍没有 active strategy：

- 生成候选策略
- 返回第一套候选
- 状态变为 `awaiting_strategy_approval`

如果已有 active strategy 且当前为 paused：

- 状态变为 `running`
- 启动执行循环

如果已经在运行：

- 只返回当前状态

### `stop_agentbox`

- 将 runtime state 设为 `paused`
- scheduler 在安全边界停止

### `read_strategy`

- 读取当前激活策略
- 返回版本元信息

### `edit_strategy`

- 以当前激活策略为基础创建草稿
- 根据用户反馈进行修改
- 标记为 `draft`
- 等待确认后再替换激活版本

在首次启动、尚未存在 active strategy 时，也允许使用同样的对话式编辑模式修改当前候选策略；不必等到已有 active strategy 之后才能编辑。

## 错误处理

系统应将错误分为：

1. 用户可处理错误
2. 可重试运行时错误
3. 致命配置错误

示例：

- gas 不足 -> 用户可处理
- RPC timeout -> 可重试
- indexer 不可用但允许自动回退 -> 可重试 / 自动回退
- 显式请求 `source=indexer` 但未配置 `INDEXER_BASE_URL` -> 配置错误
- chain id 错误 -> 致命错误
- 连续合约 revert -> 自动暂停并要求人工检查
- 合约未在浏览器开源验证 -> 用户可处理 / 发布流程不完整
- 介绍文档上传失败或未能写入 `setIntroDocUrl()` -> 可重试 / 发布流程不完整

## 读源配置

当前 `agentbox_skill` 已支持以下环境变量：

- `INDEXER_BASE_URL`
- `INDEXER_TIMEOUT_SECONDS`

推荐本地开发配置：

- `INDEXER_BASE_URL=http://127.0.0.1:8001`

建议默认策略：

- 如果配置了 `INDEXER_BASE_URL`，则 agent 默认使用 `source=auto`
- 如果没有配置 indexer，则全部回退为链上直读

## 可观测性

每轮动作循环应尽量记录：

- 为什么选了这个动作
- 当时读取到了什么状态
- 实际尝试了什么动作
- 执行结果是什么
- 更新成了什么新状态

这点非常重要，因为这个产品不只是要“执行”，还要能“解释自己为什么这么做”。

## UX 指南

系统应当：

- 用人类能理解的语言解释行为
- 不要静默替换用户确认过的策略
- 当草稿要替换 active strategy 时重新请求确认
- 在暂停、恢复时返回简洁明确的状态

系统不应当：

- 在用户无感知的情况下持续消耗 gas
- 静默替换用户已批准的策略
- 在连续失败时继续盲目运行而不提示
